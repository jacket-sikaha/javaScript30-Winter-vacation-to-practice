## 一、State 是一次 render 的 Snapshot

React 的 state 在一次 render 中是一个**快照（snapshot）**。`handleClick` 执行时，闭包里拿到的 `count` 就是当前这次 render 的值（如 `0`）。调用 `setCount` **不会立即修改**当前 render 中的 `count`。

React 不会让 setState 立即修改当前 render 的 state，而是把更新**排队并批量处理**：

- 避免一次事件中多次更新导致频繁 render，提高性能
- 保证一次 render 内的数据保持一致

### Snapshot 与闭包

```
             React Render #1
                   │
            count = 0
                   │
        ┌──────────┴──────────┐
        ↓                     ↓
 event handler             callback
        │                     │
        └─────── 闭包 ─────────┘
                              │
                              ↓
                         永远看到 #1
                         的 count = 0
```

由于函数通过闭包捕获对应 render 的 state，异步 callback 可能产生 **Stale Closure（过期闭包）**。

## 二、useEffect：依赖决定何时重新同步

### Effect 在 commit 之后运行

Effect 在**渲染提交（commit）之后**的独立阶段才运行，与 UI 计算是**分离（解耦）的**，不是并行的两条路。真实时序为：

```
render（计算 UI）→ commit（更新 DOM）→（layout effect）→ 浏览器绘制 → passive effect（useEffect）
```

Effect 负责同步外部系统，render 负责产出 UI。当 `userId` 改变，完整流程是：

```
          props userId 改变
            ↓
        组件重新 render（仍用旧 userId 计算 UI）
            ↓
        commit 提交到界面
            ↓
        React 比较 [userId]，发现变了
            ↓
        执行 Effect（在 commit 之后）
            ↓
        请求新用户
            ↓
        setState 更新自己 → 触发下一轮 render（显示新 UI）
```

```
Effect 同步外部系统的分支：
            React Render → commit
                         │
                         ↓
                       Effect
                         │
                         ↓
                  外部系统同步
             ┌──────┼──────┐
             ↓      ↓      ↓
           API    DOM    Timer
                  Subscription
```

## 三、cleanup：清理上一次的同步关系

**cleanup 的本质（面试话术）：**

> 清理 Effect 上一次与外部系统建立的同步关系，避免资源泄漏、重复订阅以及旧逻辑继续运行。

## 五、Context 性能优化：四层手段

### 第一层：稳定 Provider value

用 `useMemo` 缓存 value，避免无关状态变化导致引用变化：

```jsx
const value = useMemo(() => ({ user, setUser }), [user]);
```

**解决：** Provider 父组件无关状态变化导致 value 引用变化。

### 第二层：拆分 Context

```
UserContext
    ↓ 拆成
UserProfileContext | UserPermissionContext | UserOrderContext
```

**解决：** 不同业务状态之间相互影响。

### 第三层：减少 Context Consumer 范围

✗ 不要——把消费 Context 放进一个巨大的组件：

```jsx
function HugeComponent() {
  const user = useContext(UserContext);
  // 500 行代码
}
```

✓ 可以——抽成消费的小组件：

```jsx
function HugeComponent() {
  return <UserName />;
}

function UserName() {
  const { user } = useContext(UserContext);
  return <span>{user.name}</span>;
}
```

**解决：** 把 Context 消费限制在更小的组件里。

## 六、Fiber：可中断的渲染调度

Fiber 的意义之一，是把大任务拆成小任务并进行优先级调度：

```
大任务
↓ 拆成很多小任务
执行一部分
↓
判断有没有更高优先级任务
├─ 有 → 暂停当前工作 → 先处理高优先级任务 → 再继续之前的工作
└─ 无 → 继续执行
```

**一句话记忆（JS 单线程背景）：**

> JS 单线程 → 不能真正同时执行多个 JS 任务 → 长时间 Render 会阻塞主线程 → Fiber 把 Render 工作拆小并进行调度 → 提高页面响应性。

## 七、Fiber 相关的完整知识链与面试版

**需要串起来的知识链：**

```
Virtual DOM
↓ Diff / Reconciliation
发现哪些地方需要变化
↓
Fiber
↓ 把 Render 工作拆分 + 调度 + 优先级
可中断
↓
高优先级更新可以抢占低优先级工作
↓
Commit
↓
真正修改 DOM
```

**一句面试版回答：**

> Fiber 不是新的 Virtual DOM，而是 React 为了解决大型组件树同步渲染阻塞主线程问题而设计的内部架构。它把渲染工作拆分成可调度的工作单元，使 React 能够根据优先级中断、重新开始或继续渲染，从而让高优先级交互更加及时。
