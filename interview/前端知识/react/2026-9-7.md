## 一、主线：setState → Render → Commit

把 Fiber、Render、Commit 串起来，是 React 学习最重要的一条主线：

```
setState
↓
React 调度更新
↓
┌──────────── Render ────────────┐
│ 执行组件                        │
│ ↓                              │
│ 得到新的 React Element         │
│ ↓                              │
│ Reconciliation / Diff          │
│ ↓                              │
│ 生成需要提交的变化             │
└────────────────────────────────┘
↓
Commit
↓
修改真实 DOM
↓
useEffect 等
```

**Fiber 参与的是**：Render 工作如何被**组织、拆分、调度**。

一句话区分：

> **Virtual DOM** 解决"描述 UI 是什么"；**Fiber** 解决"React 如何组织和调度更新工作"。

### 主线的定位：startTransition

- **Fiber** 是底层的架构能力
- **startTransition** 是开发者可以使用的调度能力之一

## 三、key 的作用：identify 优先于速度

### 常见误区

问：「key 是不是为了让 Diff 更快？」

🟡 **不能简单这么说。** key 确实有助于 React 在列表 reconciliation 时判断哪些元素是相同身份、哪些发生了新增/删除/移动，从而更合理地复用现有节点。但核心**不是**"为了提高 Diff 算法速度"，**而是**为了正确识别列表元素的身份，从而正确进行 reconciliation 和复用。

> **性能是结果之一，identity（身份）才是核心。**

### 标准回答

> key 的核心作用是帮助 React 在多次 Render 之间识别列表元素的**稳定身份**，从而在 reconciliation 时正确判断哪些元素可以复用、哪些新增、删除或者移动。

### 为什么不能用 index 当 key

当列表发生**插入、删除或排序**时，index 会变化，可能导致 React 复用错误的组件实例，从而出现 **state 错位**等问题。

## 四、Context 性能问题排查与优化

**面试场景：**"Context 导致很多组件 Render，你怎么定位和优化？"

可以这样答：

> 首先使用 React DevTools **Profiler** 确认具体是哪些组件发生了不必要的 Render，然后检查 Context Provider 的 value 是否在每次父组件 Render 时产生了新的引用——如果是，可以使用 `useMemo` 稳定 value。其次，根据状态的更新频率和业务职责**拆分 Context**，避免一个 Context 承载大量互不相关的状态。对于大型状态场景，还可以**缩小 Context Consumer 的范围**，或者使用 Zustand 等支持 **selector** 的状态管理方案，减少无关组件的更新。

## 五、Hooks 规则的本质

Hooks 不允许放在**条件、循环和嵌套函数**中，本质是为了保证每次 render 的 **Hook 调用顺序稳定**，从而让 React 能正确关联每个 Hook 对应的状态。

## 六、useState vs useRef

```
useState
↓ 数据变化 → React 调度 render
产生新的 state snapshot

useRef
↓ 数据变化 → 不触发 render
所有 render / 闭包共享同一个 ref 对象
↓ 通过 ref.current 获取最新值
```

所以：

> **state 适合驱动 UI，ref 适合保存不驱动 UI 的可变数据。**

## 七、useEffect 为什么不能是 async

useEffect 的 callback **不能直接声明为 async**，因为 async callback 会返回 Promise，而 Effect 的返回值专门用于 **cleanup**。

### Effect 的完整思维模型

```
render
↓
Effect setup
↓
与外部系统同步
↓
外部系统变化 / dependency 变化
↓
cleanup
↓
重新 setup
```

## 八、受控组件

### 什么时候需要受控

当你需要让 React **实时知道并控制**这个值，比如：

- 实时校验
- 实时格式化
- 根据输入动态显示 UI
- 控制按钮 disabled
- 条件渲染
- 多个组件共享表单值
- 提交前统一处理

### "50 个字段全部受控，一定有性能问题吗？"

**不一定。** 关键看 state 更新导致的组件 render 范围和每次 render 的成本。如果表单组件很大、字段更新频繁，可以通过**组件拆分、React.memo、局部状态或字段级订阅**来降低不必要的渲染。

## 九、state 更新与引用比较

React 对 state 更新会进行**引用/值比较**；如果设置的是相同的对象引用，React 通常可以直接跳过这次更新。

### 为什么 React 推荐不可变更新

核心有三个：

1. **方便 React 判断数据有没有变化**

   React 通过引用判断：`oldUser !== newUser` → "这个 state 对象是不是换了？"

2. **对性能优化非常重要**

   前面学的 `React.memo`、`useMemo`、Context，都大量依赖引用是否稳定。

   例如 `oldUser === newUser` 可以帮助 React 判断："这个对象没变化，可以复用。"
