## 一、联合索引的运行原理（最左前缀原则）

以联合索引 `INDEX(a, b, c)` 为例。B+Tree 按 a → b → c 的顺序排序，因此查询条件必须**从最左列开始、连续地**命中，索引才能逐列定位。

四种典型情况对比：

| 场景 | 查询条件              | 各列定位情况     | 结论                                    |
| ---- | --------------------- | ---------------- | --------------------------------------- |
| A    | `a=1 AND b=2 AND c=3` | a、b、c 全部等值 | 三列都可以参与定位                      |
| B    | `a=1 AND b>2 AND c=3` | a 等值，b 范围   | b 之后的 c **不能继续定位**（可能 ICP） |
| C    | `a=1 AND c=3`         | a 等值，b 缺失   | c **不能跳跃定位**（可能 ICP）          |
| D    | `b=2 AND c=3`         | a 缺失           | 基本无法从 a 开始定位，索引基本失效     |

规律总结：

- **等值条件**：该列定位后，后面的列还能继续定位
- **范围条件**：该列本身可以定位，但后面的列失去索引定位能力
- **中间列缺失**：后面的列无法"跳过去"定位，只能在索引层面靠 ICP（Index Condition Pushdown，索引条件下推）在存储引擎层过滤。注意"只能在索引层面"——如果不走 ICP，条件照样生效，只是必须先回表取回整行、再在 Server 层判断（浪费在"取了又扔"上）

> 补充：MySQL 8.0.13+ 引入了 Skip Scan 优化，可以部分绕过"中间列缺失"的限制（把 a 的 distinct 值当作前缀枚举）。面试中主动提一句这个版本边界会加分。

## 二、EXPLAIN 的 type 等级

| type    | 触发条件                   | 含义           |
| ------- | -------------------------- | -------------- |
| `const` | 主键 / 唯一索引 + 等值查询 | 最多找到一条   |
| `ref`   | 普通索引 + 等值查询        | 可能找到很多条 |
| `range` | 索引 + 范围查询            | 范围扫描       |
| `ALL`   | 没有合适的索引             | 全表扫描       |

性能排序：`const` > `ref` > `range` > `ALL`

## 三、EXPLAIN 实例解读

```text
type: ref
key: idx_user_status_time
key_len: 8
rows: 2
Extra: Using index
```

标准解读（面试时应该能说出来的版本）：

> 这是通过联合索引进行等值查询，user_id 是索引最左列，因此可以利用索引定位；key_len=8 表示本次索引定位使用了 BIGINT 类型的 user_id。预计扫描约 2 条索引记录。由于查询所需要的 user_id、status、created_at 都包含在该联合索引中，因此形成**覆盖索引**，不需要回表。

## 四、判断索引能不能用：核心思维方式

不要死记"这个 SQL 有 WHERE，所以应该走索引"，而是问：

> **B+Tree 能不能根据这个条件快速确定一个连续的范围？**

两个容易误解的概念：

1. **索引失效的准确理解**
   - ❌ 索引失效 = MySQL 完全不使用索引
   - ✅ 索引失效 ≈ 无法通过索引获得高效的访问路径

2. **索引选择性**
   - 索引选择性 ≈ 能把数据过滤掉多少（过滤能力越强，索引越高效）

## 五、面试参考回答：组合索引为什么有效

**面试官问：为什么建立 `(user_id, status, created_at)` 组合索引？**

不要只回答："因为可以同时索引三个字段。"——这个答案太浅。

更好的回答：

> 因为查询条件中 user_id 和 status 是等值条件，created_at 是范围条件。按照 (user_id, status, created_at) 建立联合索引后，MySQL 可以利用 B+Tree 的有序性，先通过 user_id、status 缩小搜索范围，再在对应范围内定位 created_at，从而减少需要扫描和回表的数据量。

## 六、实战：ORDER BY + LIMIT 查询的执行过程

```sql
SELECT *
FROM orders
WHERE user_id = 100
  AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```

假设这条查询使用的联合索引是 `(user_id, created_at, status)`，执行过程可以理解为：

```
B+Tree
  ↓
定位 user_id = 100 的范围
  ↓
该范围内按 created_at 有序
  ↓
从 created_at 最大的方向开始扫描
  ↓
逐条：ICP 检查 status = 1
  ↓
凑满 20 条即停止
  ↓
（每条通过的记录当场回表拿完整数据）
```

## 七、关键纠正：status 的过滤靠 ICP，不是索引定位

status 虽然存在于索引中，但它在 `(user_id, created_at, status)` 里位于 created_at 之后——**created_at 后面的 status 不能用于进一步缩小 B+Tree 的搜索范围**。

但 MySQL 可以利用 ICP（Index Condition Pushdown，索引条件下推）在扫描索引阶段就完成过滤：

```
扫描索引
  ↓
发现 status = 1？
  ├─ 否 → 直接丢弃，不必回表
  └─ 是 → 回表
```

所以更准确的说法是：

> 利用 B+Tree 的有序性，通过 user_id + created_at 定位并维持排序；status 作为 ICP 条件在索引扫描阶段过滤，从而减少不必要的回表。

## 八、三个核心概念：Range Scan / ICP / 回表

| 概念               | 作用                                           |
| ------------------ | ---------------------------------------------- |
| ① Index Range Scan | 决定扫描 B+Tree 的**哪个范围**                 |
| ② ICP              | 对扫描到的索引记录继续做**条件过滤**，减少回表 |
| ③ 回表             | 真正去**聚簇索引**拿完整数据                   |

一条记忆链：

```
B+Tree
  ↓ 先确定「去哪找」
Index Range
  ↓ 再判断「哪些不要」
ICP
  ↓ 最后拿完整数据
回表
```

## 九、EXPLAIN 补充：rows 与 filtered

| 字段       | 含义                                 |
| ---------- | ------------------------------------ |
| `rows`     | 预计要看多少行？                     |
| `filtered` | 预计这些行里有多少比例能通过 WHERE？ |

## 十、EXPLAIN 字段速查

| 字段       | 应该怎么理解                                                      |
| ---------- | ----------------------------------------------------------------- |
| `key`      | 最终选择了哪个索引                                                |
| `key_len`  | 这个索引实际用了多长（多少字节参与定位）                          |
| `rows`     | 优化器估算要扫描多少行                                            |
| `filtered` | 扫描出来的行预计有多少 % 能通过条件                               |
| `Extra`    | 执行过程中的额外信息，例如 `Using index`、`Using index condition` |

## 十一、易混点：`Using index` ≠ `Using index condition`

这两个 Extra 提示名字非常像，面试官爱考，务必分清：

| Extra                   | 含义                                         | 回表？                   |
| ----------------------- | -------------------------------------------- | ------------------------ |
| `Using index`           | **覆盖索引**：查询所需列全在索引中           | 不回表                   |
| `Using index condition` | **ICP**：部分 WHERE 条件下推到存储引擎层过滤 | 仍需回表（只是减少次数） |

一句话区分：`Using index` 是"根本不用回表"，`Using index condition` 是"回表前先在索引上筛一遍"。

## 十二、总结：联合索引列顺序的设计原则

联合索引的列顺序没有固定公式，应根据实际情况综合决定：

- **实际查询条件**：等值条件在前、范围条件在后，让最左前缀尽量完整命中
- **选择性**：区分度高的列优先，过滤能力强
- **排序需求**：ORDER BY 的列放进索引，可借助 B+Tree 有序性避免额外排序
- **范围条件**：范围列放最后，避免截断后续列的定位能力（后续列仍可 ICP 过滤）
